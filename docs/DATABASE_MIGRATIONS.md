# Database migrations

Authoritative history (`prisma/migrations/`, applied in this order):

| # | Directory | Contents |
|---|---|---|
| 1 | `20261009000000_baseline_modules_1_4` | Modules 1-4 (+5A, no schema change): 25 tables, 16 enums, 58 index statements, 39 foreign keys. Generated by Prisma's schema engine from the schema as of Module 5A, then committed verbatim under an 11-line comment header. |
| 2 | `20261010120000_add_business_ai_preferences` | Module 5B.1 (additive): 2 enums, table `business_ai_preferences`. |
| 3 | `20261011120000_add_business_memories` | Module 5B.2 (additive): 2 enums, table `business_memories`. |

`schema.prisma` is the source of truth. Migrations 2 and 3 were not modified by the baseline work. **Never edit a migration after it has been applied anywhere** (Prisma checksums them); add a new migration instead.

## A. Fresh database (empty Postgres)
```bash
export DATABASE_URL=postgresql://...            # an EMPTY database
npx prisma migrate deploy                         # applies 1, 2, 3 in order
npx prisma generate
```
Production and CI must use `migrate deploy`, never `migrate dev` / `db push`.

## B. Existing database that was created earlier with `db push` (tables already exist)
The baseline must **not be executed** (every `CREATE TABLE` would fail, or worse). Record it as already applied, then deploy the rest:
```bash
export DATABASE_URL=postgresql://...            # the EXISTING database
# 0. take a backup first.
npx prisma migrate resolve --applied 20261009000000_baseline_modules_1_4
npx prisma migrate deploy                         # applies only 2 and 3 (additive)
```
Before the `resolve` step, confirm that the database really matches the Modules 1-4 schema (it must have been created from the Module 4/5A schema, not a modified one). The reference schema is kept as a fixture:
```bash
npx prisma migrate diff --from-url "$DATABASE_URL" \
  --to-schema-datamodel scripts/migration-verification/fixtures/schema-modules-1-4.prisma --exit-code
```
Exit code 0 = identical, 2 = differences. On 2, stop and investigate: do not baseline a database that differs, because `resolve --applied` would record a lie. (Rehearsed here through the WASM harness, not through this CLI command; see the last section.)

## C. Check that history and schema agree (CI gate)
```bash
npx prisma validate
npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma \
  --shadow-database-url postgresql://.../shadow --exit-code      # exit 0 = no drift
```

## What was verified, and what was not
See `PRE_5C_RELEASE_GATE_REPORT.md`. In short: the three-migration chain was applied to an empty PostgreSQL 16, produced no drift against `schema.prisma` (with a positive control), and the existing-installation path (B) was rehearsed with seeded data left byte-for-byte unchanged. That evidence came from **Prisma's schema engine run as WebAssembly (6.19.0) through `scripts/migration-verification/`, not from the `prisma` 6.2.1 CLI**, whose engine downloads were blocked. The exact CLI commands above have therefore **not** been executed here and must be run once in a networked environment before the first production deploy.

## Real-database application verification
`scripts/http-verification/` runs the application over HTTP against a migrated disposable Postgres and Redis (see its README). It is separate from the unit tests and from the migration harness above.
